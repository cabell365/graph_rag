01 / CANYON COMMONS

Start with relationships

A relational database organizes data into tables and joins. Neo4j stores identifiable nodes and explicit connections. Both can represent the same facts; a graph is particularly useful when the question follows several kinds of connections.

For example: who owns an account, which approved products come from a supplier, and which supplier incident might call for outreach? Following those relationships is easier to inspect when the paths are visible.

02 / CANYON COMMONS

Nodes, labels & properties

ConceptExampleHow to read it
Node(r:SalesRep)r is a variable representing a representative node.
Label:SalesRepThe category of the node; Entity is an additional shared label.
Property{id: "REP-100001"}An attribute used for stable identity.
Relationship-[r:MANAGES]->A directed, typed connection with optional provenance.
Path(rep)-[:MANAGES]->(customer)-[:APPROVED_FOR]->(product)A connected sequence of facts.

Use IDs to identify objects. Names can change or collide. Relationships have direction, although queries can choose to traverse either direction. A label is not a table, and a node can have several labels.

03 / CANYON COMMONS

Your first Cypher query

Open Neo4j Browser at http://localhost:7474 after following the README. Sign in with your private local credentials. Run a read-only query:

MATCH (r:SalesRep {id: "REP-100001"})
RETURN r.id, r.name;

MATCH describes the pattern to find. RETURN selects what to show. The next query follows ownership and returns the supporting relationship:

MATCH (r:SalesRep)-[owns:MANAGES]->(c:Customer {id: "CUS-001"})
RETURN r.name, c.name, owns.document_id;

A result names the owner and a source document. Read that document before making a broader claim.

04 / CANYON COMMONS

Think in paths

MATCH (c:Customer)-[:APPROVED_FOR]->(p:Product)
      -[:SUPPLIED_BY]->(s:Supplier {id: "SUP-01"})
RETURN DISTINCT c.id, c.name, p.id;

This is a supplier-to-product-to-customer connection. It identifies approved accounts worth checking. It cannot establish that an order exists or that an incident caused lost sales. DISTINCT removes repeated result rows, not repeated truths.

05 / CANYON COMMONS

Creating data safely

These examples are illustrative. The importer performs writes; use the dedicated project database for experiments.

CREATE CONSTRAINT entity_id IF NOT EXISTS
FOR (e:Entity) REQUIRE e.id IS UNIQUE;

MERGE (e:Entity:Customer {id: "CUS-DEMO"})
SET e.name = "Demonstration account";

CREATE always creates a new object. MERGE reuses the matching pattern or creates one. The unique ID constraint protects identity across reruns. For relationships, match both endpoints first, then MERGE the relationship. Never concatenate question text into Cypher; parameterize values in Python.

graph.query(
    "MATCH (c:Customer {id:$id}) RETURN c.name AS name",
    id="CUS-001"
)
06 / CANYON COMMONS

Indexes & search

A uniqueness constraint helps identity lookups. A full-text index finds matching words. A vector index finds semantically related passages. Semantic similarity is useful retrieval evidence, but it does not prove a statement is true.

Search typeStrengthLimit
ID lookupExact object resolution.You need the correct identity.
Full textSpecific names, product codes and terms.Vocabulary mismatch can reduce recall.
Vector searchSimilar meaning even with different wording.Approximate neighbors can be irrelevant.
Graph traversalRelated objects and supporting documents.Edges have scope and provenance; paths are not causal proof.

The app combines keyword and vector rankings with RRF and then follows relevant relationships. Nomic generates document and question embeddings with the appropriate search prefixes. Vector dimensions come from the model output rather than an assumed number.

07 / CANYON COMMONS

From search to Graph RAG

  1. You ask a question, optionally with a sidebar event date.
  2. Nomic turns the question into a query vector. Neo4j searches vectors and words.
  3. The application fuses ranked results, resolves entities and explores related paths.
  4. Supporting source passages and exact finance results become evidence.
  5. Mistral writes an answer with document citations.
  6. You inspect passages, validity dates and query provenance in the evidence desk.

The model is a language interface to evidence. It should say when the evidence is missing, ambiguous or historical.

08 / CANYON COMMONS

Dates, history & evidence

A contract can expire while remaining useful for a historical question. A policy document marked “current” can be current only within 2018–2024. Set an event date when asking about discounts, contracts or incidents. With no date, expect the assistant to ask for timing.

QuestionEvidence to checkMistake to avoid
What did A4 cost in June 2023 for CUS-001?Catalog, account and dated contract for PRD-101.Using another account’s price or stacking a prohibited discount.
Who might need outreach after an A4 delay?Supplier → product → approved customer → account owner.Calling an eligible customer a proven affected buyer.
Why did a rep miss target?Actual/target data plus independently proven causality.Treating a supplier bulletin as proof of lost sales.
What policy applies today?Verified current policy; none is supplied after 2024.Extending a fictional historical policy into 2026.
A source citation is the beginning of verification. Check the quoted passage, its scope and its dates.
09 / CANYON COMMONS

Working with the financial graph

The backup has representative-level monthly actual and target sales. The application creates a MonthlySales node per rep/month/year and a shared Period node per calendar month.

MATCH (:SalesRep {id: "REP-100001"})-[:HAS_METRIC]->(m:MonthlySales)
WHERE m.year = 2018 AND m.month_id = 1
RETURN m.target_sales, m.actual_sales, m.source, m.source_sha256;
MATCH (m:MonthlySales) WHERE m.year = 2023
RETURN sum(m.actual_sales) AS actual,
       sum(m.target_sales) AS target, count(m) AS source_rows;

Use the Finance explorer for clear rep/team/network filters and automatically attached query provenance. Team membership is the dump’s current mapping, not a time-valid roster. The workbook is a separate sample; its people are not silently merged into the SQL graph.

Glossary

TermMeaning in this application
NodeAn identifiable graph object, such as a customer, representative, document or monthly metric.
LabelA node category such as SalesRep, Customer or Document. A node may have more than one label.
RelationshipA typed, directed connection between two nodes, with optional properties.
PropertyA stored attribute: a name, stable ID, date, amount or source reference.
CypherNeo4j’s declarative pattern query language.
MERGEMatch a pattern if present, or create it. Constraints prevent duplicate identities.
ConstraintA database rule such as unique Entity.id.
IndexA structure that accelerates lookup, including vector and full-text indexes.
EmbeddingA vector describing a text passage or question for semantic similarity.
ChunkA bounded text passage, linked to its original Document.
RAGRetrieval augmented generation: a language model answers using retrieved evidence.
Graph RAGRAG that uses graph structure to find related entities and supporting sources.
RRFReciprocal rank fusion: combine ranked vector and keyword results without comparing their raw scores.
ProvenanceWhere a claim or value came from, including document ID or dump hash and query filters.
Validity windowThe dates during which a documented rule or contract applies.
Natural keyThe source tuple (rep ID, month ID, year ID) that identifies a monthly metric.
IdempotenceRerunning the same import preserves the same logical IDs.
HallucinationA model claim not supported by evidence; citations alone do not guarantee correctness.
BoltThe database protocol used by the Python driver.
FixtureA supplied reference graph describing this fictional scenario; it is not newly inferred truth.
